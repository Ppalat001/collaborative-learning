Dissertation research platform · Complete reference

How the application works — flow, business logic and metrics

A complete walkthrough of the AI-Supported Collaborative Learning platform: what students and the researcher see, every rule the server enforces, how AI support is generated, how the shared answer is tracked character by character, what is stored, and exactly how every exported metric is calculated.

1.Overview

The application is the research instrument of a dissertation on how AI support affects collaborative learning. Small groups of real students (2–4 per group, each on their own device) work through 10 short scenarios. Every scenario has three steps on one page:

Step 1 · DiscussLive group chat about the scenario.
→
Step 2 · Private AIEach student may switch on AI support types; only they see the replies.
→
Step 3 · Shared answerEveryone types one answer together; each person’s text has their colour.
→
“I am good”When every member confirms, the scenario is finished.

Around the scenarios, each student completes a pre-test (8 multiple-choice + 2 written questions), a short rating after every scenario, a post-test and an end questionnaire (10 open questions). A password-protected admin page lets the researcher download per-group CSV files, score answer quality with a blind rubric, and delete test data.

Three design principles

AI supports, it doesn’t do

The AI is instructed to scaffold thinking and never write the group’s answer — except the deliberately chosen “Full expert answer”, which is recorded as the most direct level of help.

AI is private

Only the requesting student sees a reply. Any AI idea must be brought back to the group by a person, which makes the influence of AI on collaboration observable.

The answer is truly shared

One text box, simultaneous typing, every character attributed to its author, and the group moves on only when all members agree.

5.Groups, names and identity

Creating a group

On the home page the first student types their name and clicks Create group session. The browser calls POST /api/sessions, which creates a session with a random group ID GROUP-XXXX (4 characters from ABCDEFGHJKLMNPQRSTUVWXYZ23456789 — no O/0/I/1 to avoid confusion), then immediately calls the join endpoint so the creator becomes the first member. The event session_created is logged.

Joining a group

Other students enter the group ID and their name and click Join → POST /api/sessions/{code}/join. The server enforces:

RuleResult if broken
Group ID must exist400 “Session not found”
Name is required (extra spaces collapsed and trimmed)400 “Please enter your name to join the session”
Name at most 40 characters400 “Names can be at most 40 characters”
Name unique within the group (case-insensitive)400 “Someone in this group already uses the name …”
At most 4 members per group400 “Session is full (maximum 4 participants)”

On success the server creates a participant with an internal UUID, an anonymous code P-XXXXXXXX (used for anonymised reporting) and the join time, and logs participant_joined.

How the app remembers a student

The browser stores participantId and participantName in localStorage. Every later request sends participantId, and the server verifies it belongs to that group (getParticipantInSession). Consequences:

  • A student must keep the same browser and device for the whole study.
  • Reloading a page is safe; clearing browser data or switching device loses the link to earlier contributions.
  • If the scenario page is opened without a stored identity, it shows a warning: “Join from the home page with the group ID and your name.”

Member colours

Members get a colour by join order: 1st indigo 2nd green 3rd amber 4th rose. The same colour is used in the chat and in the shared answer.

6.Lobby, consent and pre-test

Lobby (/session/{code})

  • Group ID card: large group ID, “You joined as <name>”, and a Copy group ID button.
  • Participant list: all members, the current student marked “(you)”. Refreshes every 3 seconds.

Consent

One member ticks the consent box and clicks Record consent → POST /api/sessions/{code}/consent. Consent is stored once for the whole group (sessions.consent_given) and consent_given is logged.

Pre-test

After consent, each student completes the pre-test individually → POST /api/sessions/{code}/assessment with assessmentType: "pre".

  • 8 multiple-choice questions, one per concept (definition, interdependence, accountability, scaffolding, choosing support, over-reliance, group agency, disagreement) — all required.
  • 2 written questions — required.
  • Score = number of correct options (0–8), computed on the server.
  • Stored: chosen option index per question, written answers, score, max score, completion time. Logged as assessment_completed.
  • Only once per student; a repeated submission returns the existing result.
Begin scenariosThe button is enabled only when consent is recorded and this student completed their own pre-test. It opens scenario currentScenarioIndex + 1, so a returning student continues where the group is.

7.The scenario page

URL: /session/{code}/scenario/{1–10}. On load the page calls GET /api/sessions/{code}/scenario/{n}?participantId=…, which returns the scenario text, the chat history, the members (with colours), this student’s own AI replies, the shared answer with authorship, the list of “ready” members, whether it is submitted, and whether this student already rated it.

The first time anyone opens a scenario, the server creates the group’s attempt for that scenario (getOrCreateAttempt), stores discussion_started_at and logs scenario_started. This start time is the reference for all “minutes” metrics.

The header shows the scenario number and title, a “Group GROUP-XXXX” badge, “Signed in as <name>”, and a live indicator (connected / reconnecting, number of members online). All three steps are visible at once so students can move freely between discussing, consulting AI and writing.

8.Step 1 — Group chat

Student A types message → POST /api/sessions/{code}/messages server checks: text not empty · ≤ 2,000 chars · A is a member · scenario not finished server saves message (author, scenario, created_at) → returns it A's browser shows it → emits socket "chat:message" → server relays to room → B, C, D show it instantly
  • Messages show author name, colour and time.
  • Saved first, then broadcast — a message on screen is always in the database.
  • On (re)connection the page reloads the full history and merges it by message ID (no losses, no duplicates).
  • After the scenario is finished, the chat is read-only (409 “This scenario has already been submitted”).
  • The chat transcript (“Name: text” per line) is sent to the AI as context in Step 2.

Students can select any number of options or none. Selecting nothing = “no assistance” (level 0).

What happens when a student selects an option

Student ticks "Small hint" → POST /api/sessions/{code}/scaffold {action:"select", scenarioOrder, scaffoldingType, participantId} ├─ reply already stored for (student, scenario, type)? → mark shown, times_shown +1, return cached (no AI call) │ event ai_support_reselected (if it was hidden) └─ not stored yet: scenario finished? → 409 "no new AI support can be requested" build prompt (system + context) → call OpenAI → save reply → event ai_support_requested return reply → shown in amber "AI response" box under the option (only to this student) Student unticks → {action:"unselect"} → hidden, times_hidden +1, event ai_support_unselected

The prompt sent to the AI

Instructions (system prompt)

“You are a learning support agent in a collaborative educational research study. Your role is to scaffold group learning — never to replace human collaboration or autopilot the task. Keep responses concise (2–4 short paragraphs)… One member of the group asked for this support privately. Speak to them directly and help them bring better ideas back to their group rather than writing the group’s answer…”
+ the specific rules for the chosen type (table above).

Context (user message)

Scenario title · task type · description · prompt for the group
Group discussion so far (full chat transcript, “Name: text”)
Group answer written so far
→ So the help is tailored to what this group actually discussed and wrote.

The OpenAI call

  • client.responses.create({ model, instructions, input, store: false, max_output_tokens: 800, reasoning: { effort: "none" } })
  • Model from OPENAI_MODEL (study: gpt-6-luna; default gpt-4o-mini). Optional OPENAI_BASE_URL.
  • store: false — OpenAI does not keep the conversation.
  • If the model rejects an optional parameter, the server automatically retries without it.
  • Errors are translated into understandable messages (invalid key 401, no credit / rate limit 429, unknown model 404) and returned as 502; the key is never revealed.
  • Response time is measured (ai_latency_ms).
  • Mock mode: without OPENAI_API_KEY, a fixed example reply per type is returned with model "mock"; exports flag it as real_ai_response = no.

Caching and integrity

  • A unique database index on (student, scenario, type) guarantees one reply per student per scenario per type. Double clicks or simultaneous requests cannot create duplicates (insert uses “on conflict do nothing” and re-reads).
  • Toggling never calls the AI again; it only changes selected and increments times_selected / times_unselected.
  • Stored with each reply: the exact instructions and context sent, model, latency, created time, last toggle time.
  • After the scenario is finished, new replies cannot be requested, but existing replies can still be shown or hidden by their owner.
  • Replies are never sent to other members — not via API, not via socket.

10.Step 3 — The shared group answer

All members type in one text box simultaneously. Each person’s text is highlighted in their colour:

Collaboration means building understanding together, not just splitting the work, because everyone must be able to explain the final result.

Above the box: a member bar with each name, share of the current text (%) and status (editing / “I am good”). Below: word counter “n / 500 words” (red at the limit).

What happens on every keystroke (useCollaboration hook)

  1. Diff — the new text is compared with the previous text to find the single changed region (common prefix and suffix kept): start position, characters removed, inserted text.
  2. Authorship update — the answer’s authorship is a list of runs [{participantId, length}, …] covering every character. Removed characters are cut out of the runs; inserted characters become a run for the typist; adjacent runs by the same person merge.
  3. Live broadcast — socket field:update (text + authorship) → server stores it as the room’s latest state in memory → field:state to the other members, whose screens update instantly.
  4. Debounced save — after 0.8 s without typing: POST /api/sessions/{code}/sync with text, authorship and the batch of edits (chars added, chars removed, inserted text) → stored in scenario_attempts + one edit_events row per batch.
  5. Flush — on leaving the page (keep-alive request) and before “I am good”, unsaved changes are sent immediately.

Server checks when saving

ConditionResponse
Scenario already submitted409 “This answer was already submitted”
This student is marked “I am good”409 “Unselect "I am good" before editing”
More than 500 words400 “The answer is limited to 500 words”

The editor also refuses typing that would exceed 500 words (deleting is always allowed). Authorship received from the browser is normalised on the server so the runs always cover exactly the answer length (anything untracked is attributed to “nobody”).

Late joiners and reconnects

When a member opens the page, they load the saved version from the database; if the server holds a newer live version in memory (room:state), that is applied. Live edits that already arrived are never overwritten by an older database copy.

11.“I am good” and submission

Student clicks "I am good" → flush unsaved typing → PUT /api/sessions/{code}/scenario/{n} {action:"ready", ready:true} in ONE database transaction: answer empty? → 400 "Write the group answer before selecting I am good" add student to ready list → event participant_ready every member in ready list? yes → submitted = true, submitted_by, final_answer_at = now sessions.current_scenario_index = n (progress) n = 10 → sessions.completed_at = now event final_answer_submitted → socket "ready:update" → all screens update (status chips, lock, rating form)
  • A ready student cannot type (button state + server 409). Clicking again (“ready: false”) removes readiness → participant_unready, and they can edit again.
  • Readiness of others is not reset when someone edits; each member decides when to un-ready.
  • The transaction makes simultaneous last clicks safe: the scenario is submitted exactly once.
  • After submission: chat, answer and new AI requests are locked; the rating form appears.

14.Post-test, questionnaire and the end

Page /session/{code}/complete, in this order:

  1. Post-test — 8 new multiple-choice questions on the same 8 concepts (so learning can be compared per concept without memorising answers) + the same 2 written questions as the pre-test (direct before/after comparison). Required, scored 0–8, once only, logged assessment_completed.
  2. End questionnaire — 10 open questions, all optional, saved once → POST /api/sessions/{code}/reflection, logged final_reflection_submitted.
  3. Thank-you page — “study complete” with the student’s post-test score.

16.Researcher admin page

Access

/admin. Every admin request must carry the password (header x-admin-password or ?password=) equal to ADMIN_PASSWORD. In development without that variable the password is research-admin; in production without it the admin area is disabled (never falls back to a public default).

Groups

Load groups lists all groups (newest first): group ID, member names, finished scenarios, created date.

Downloads — always per group

The researcher selects a group and downloads one of 8 CSV files (GET /api/admin/export?type=…&session=GROUP-XXXX; refused without a group). Files open in Excel, SPSS, R or Python. All files use names and anonymous codes, readable values (“Small hint”, “yes/no”, 0–100 %) and UTC times. Details in section 17.

Clean up data

  • Delete one group — type its group ID to confirm → DELETE /api/admin/sessions?session=CODE with {confirm: CODE}.
  • Delete all — type DELETE ALL → ?all=1.
  • Deleting a session cascades to everything linked: members, attempts, messages, AI replies, edits, ratings, tests, questionnaires, events and rubric scores.

Rubric scoring

  • Lists every finished group answer (GET /api/admin/rubric?rater=…).
  • Rater enters name/initials, then scores 6 criteria from 1 Weak · 2 Developing · 3 Good · 4 Strong: correctness, clarity, reasoning, completeness, use of examples, depth of understanding; optional notes.
  • Total 6–24; average = total / 6.
  • Blind mode (default on) hides which AI support the group used.
  • One score per rater per answer; saving again updates it. Multiple raters → inter-rater reliability.
  • Also shows a summary of how often each support type/level was used.

18.Metrics and formulas

All derived metrics are computed at export time from the raw stored data (nothing is pre-aggregated), so formulas can be changed later without losing information.

Before / after AI

first_ai_at(scenario) = earliest AI request by ANY member in that scenario
message is "before AI" ⇔ no AI was requested OR message.created_at < first_ai_at

Used by chat_messages_before_ai/after_ai, before_or_after_ai and answer_matches_chat_before_ai_percent. Because AI is private, “after AI” means “after someone in the group had access to AI help”.

Text overlap (“copied from AI”, “matches chat before AI”)

words = lowercase, punctuation removed, split on spaces
trigrams(T) = set of every 3 consecutive words in T
overlap(answer, source) = |trigrams(answer) ∩ trigrams(source)| ÷ |trigrams(answer)| × 100

Example: answer “students should explain their reasoning to each other” has 6 trigrams. If the AI reply contains “…explain their reasoning to each other…”, 4 of them are shared (explain their reasoning, their reasoning to, reasoning to each, to each other) → 67%. Three-word sequences detect re-used phrasing while ignoring common single words. Blank when the answer has fewer than 3 words or no AI was used.

InterpretationHigh overlap with AI suggests wording was taken over (possibly paraphrased lightly); low overlap does not prove that no AI ideas were used — only that the wording differs.

Authorship and answer share

authorship = runs [{participant, length}, …] covering every character of the final answer
chars_by_author(p) = Σ length of runs by p
share_of_final_answer(p) = chars_by_author(p) ÷ answer length × 100

Authorship reflects who typed the characters that survive in the final text. Text a student typed and someone else deleted does not count here, but does count in characters_typed_in_answer. In answer_written_by, percentages are relative to all attributed characters; untracked text (rare, e.g. legacy data) is attributed to nobody.

Participation balance (0–1)

activity(p) = chat characters by p + characters added by p in the answer
share(p) = activity(p) ÷ Σ activity
balance = −Σ share(p) · ln share(p) ÷ ln(number of members)

Normalised Shannon entropy: 1 = perfectly even, 0 = one person did everything. Example with 2 members at 70% / 30%: −(0.7 ln 0.7 + 0.3 ln 0.3) / ln 2 = 0.88. Blank with fewer than 2 members or no activity. Members with zero activity count in the denominator (they pull the balance down).

22.Real-time layer (Socket.IO)

Each browser joins a room per group and scenario: GROUP-XXXX:n. The socket only relays; the database (via the API) remains the source of truth.

EventDirectionEffect
room:joinbrowser → serverJoin the room; server replies participant:joined (online count) and, if it holds live state, room:state.
field:updatebrowser → serverNew answer text + authorship; stored in memory and broadcast as field:state.
chat:messagebothRelay of an already-saved message.
ready:updatebothRelay of new readiness / submission state.
disconnect—Server sends participant:left with the new count.

Room state in memory is lost on server restart; nothing is lost from the research data, because every change is also saved through the API.

23.Reliability, security and privacy

Data integrity

  • All rules enforced on the server, not only in the browser.
  • Transactions for readiness/submission; unique index for AI replies; once-only submissions.
  • Continuous saving (0.8 s) + flush on leave; at most a fraction of a second of typing can be lost.
  • SQLite WAL mode + 8 s busy timeout for concurrent writes; foreign keys enforced.
  • Lazy database opening, so builds on Railway don’t lock the file.

Security & privacy

  • Admin protected by ADMIN_PASSWORD; disabled in production if unset.
  • OpenAI key only on the server; never sent to browsers or shown in errors.
  • store: false for OpenAI calls.
  • Anonymous codes in every export for anonymised reporting.
  • AI replies only returned to their owner.
  • Consent recorded before any study activity.
NoteStudents have no passwords: anyone who knows a group ID and an unused name could join a group with free places. Share group IDs only with the intended members.

26.Limitations and known gaps

Design limitations

  • Self-selection of AI: all groups have the same options and choose freely, so comparisons are “chose AI vs didn’t”, not randomised conditions. Causal claims need assigned conditions (e.g. no-AI vs AI groups).
  • Device-bound identity: switching browser/device breaks the link to earlier data.
  • Overlap ≠ idea use: paraphrased AI ideas are not detected by trigram overlap.
  • No background data: age, study year, prior AI use and attitudes are not collected.

Stored but not exported

  • Research event timeline (incl. “I am good” on/off switching).
  • AI response time (ai_latency_ms) and exact prompts sent.
  • Typing history (edit_events) — allows reconstructing how the answer evolved.

Not captured

  • Connection drops / presence over time (in memory only).
  • Paste vs typing (batches of 0.8 s can’t distinguish them reliably).
  • Whether a student carried their private AI idea into the chat (could be computed from stored data: overlap of the student’s post-request messages with their own reply).
  • Which member typed the AI-matching phrases in the answer (computable from authorship + replies).
